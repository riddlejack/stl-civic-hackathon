# Precedents for a closed loop: what Cityworks does natively, who publishes completed-versus-closed, and what the St. Louis geoportal shows

Web research only, 14 Oct 2026. Labels: **observed** (opened today), **reported** (a source says so), **inferred** (my conclusion), **unverified** (background knowledge). Working logs with every URL and retrieval time: `build/E2/work/` (request and work-order numbers from other cities' public pages are redacted there; originals in git-ignored `build/E2/private/`). Figures: `build/E2/figures.json`; facts: `research/precedents-closed-loop-facts.csv` (built by `build/E2/build_facts.py`).

## Summary

**A2 in one sentence: Cityworks already closes a linked service request automatically when its work order is closed, so rule 2 is "link the job and stop closing the request by hand", not a nightly SQL job** (**observed**: [Close a Work Order](https://help.cityworks.com/AMS/OC/Content/AMS/OC/WorkOrder/CloseAWorkOrder.htm), [Close a Service Request](https://help.cityworks.com/AMS/OC/Content/AMS/OC/ServiceRequest/CloseAServiceRequest.htm), Cityworks 23; St. Louis runs CW 23.10 per its own query service). No preference controls it. In St. Louis it can rarely fire, because requests are closed by hand at the hand-off, even Forestry's linked tree removals ("removal work order created") (inferred from the sibling thread's status-page checks). In DC's public Cityworks data, 84–90% of linked requests closed within a minute of their work order (FY2018–19 samples). The city's own CSB definitions (archived June 2025; page inactive since September 2025) said Closed means the work "has been finished by the department".

Rules 1 and 4 are native too: create or attach a work order from the request; saved search to eURL to an ArcGIS Dashboard, which the city's portal has installed. Rule 3 is partly new work: nothing copies the request's promise date to the work order, but once rule 2 holds the overdue list can run on open requests.

Of 11 cities, none publishes done-by-promise per request type or an overdue list by department. New York and Boston publish close-against-target per type (Boston's series is empty today); Baltimore and Denver separate "work completed" from "closed" in a public field. Chicago closes a request only with its last work order and shows residents each work order's status; Houston (2022) and Toronto (2023) put "stay open until the work is done" in writing. On the geoportal, 7 of 166 public city maps read Cityworks; none of the 4 public dashboards does, and none shows data today.

**Inferred, for the entry.** Rule 2 does not need a nightly SQL job, and a nightly job would be the wrong design: custom database work is what a cloud migration strips out. The product already closes a linked request when the crew closes the job. What the city has to change is practice and status values: link the job at hand-off, and set the request to a not-closed status (the city's own "Dispatch" or "Pending") instead of closing it.

**Reading the table (inferred from the rows above).**
- **Promise per request** is common: 5 of 11 publish a due date or SLA on each request (Houston, San Antonio, Baltimore, Philadelphia, Boston); Chicago shows residents the first work order's SLA; Denver publishes promised days per type without a per-row date.
- **A city-published on-time share per request type**: 2 of 11, both graded on the close, not the finished job. New York publishes "percent meeting time to close" (or "to first action") per SR type annually in the Mayor's Management Report. Boston's CityScore defines on-time per type, but every 311 series is null in the latest snapshot. Houston grades it monthly in an internal report.
- **Completed separated from closed** in a public field: Baltimore (`Outcome` "Work completed"), Denver ("Closed - Service Completed" vs "Closed - Scheduled"), Boston partly (Resolved / Noted / Transitioned). In text only: New York, Austin, Houston. Chicago builds it into the structure (request closes with its last work order). **None publishes a completed-versus-closed share.**
- **Done by the promised date per request type** (work finished, not request closed): **none of the 11 publishes it.** Nor does any publish an overdue list by department; Baltimore and San Antonio publish the fields needed to build one.
- **Written rules that the request stays open until the work is done**: Houston (A.P. 2-23, 2022), Chicago (by design, per its inspector general), Toronto (2023 budget note), Kansas City (2018 design for its new CRM; current practice not established). The opposite, admitted in writing: Louisville's data dictionary, Philadelphia's explainer ("resolve … but not close"), Denver's auditor, New York Parks' closure text.
